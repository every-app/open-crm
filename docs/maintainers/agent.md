# The research agent

The CRM keeps its records up to date with a research agent ported from the CRM's agent (which ran on Vercel). Here it is a [Think](https://developers.cloudflare.com/agents/) agent in a Durable Object (`CrmAgent`, `src/server/features/agent/CrmAgent.ts`), driven by a queue in the database and the Worker's minute cron. Every model and Context.dev call goes through the Every App gateway, named for the organization it is for (`docs/maintainers/every-app.md`).

**The model** is GPT-6 Luna through OpenRouter, set up as OpenSEO runs Luna (`src/server/lib/openrouter.ts`), with MiniMax M3 where OpenAI is blocked, and nobody picks it in the app; a self-hosted copy sets `OPENROUTER_MODEL` to use another. As OpenSEO splits it, a person's chat turn (a record chat or Chat) reasons at `max` with 16,000 output tokens a step, and background work (research sessions, team agent runs, compaction summaries) at `low` (`runtime/model.ts`, `runtime/turn.ts`). A run records the model it ran on.

## The queue

`agent_task` says what the work is: a kind (`src/shared/agent-tasks.ts`), a subject (a company, contact, deal or the workspace), a reason, a priority and when it is due. A partial unique index allows one open task per organization, kind and subject, so queueing the same work twice is a no-op (`AgentTaskRepository.insertIfAbsent`). Anything that recurs ("check again in 30 days") is a task's `due_at`, never a timer.

Work is queued by the features that cause it, through `AgentTaskService`: a new company or contact, a changed workspace website, a new or backfilled custom field the agent fills, a person asking for a recheck, a read of the connected Slack workspace. A CRM event for the team agents is an `agent-event` task too, written by the record write itself (Team agents, below).

## The dispatcher

The minute cron (`src/server/cron.ts` → `scheduled.ts`) closes stale tasks, then drains two lanes across every organization (`dispatch.ts`, numbers in `dispatch/config.ts`):

- **Visible** (`brand`, `portrait`, `slack-sync`): no model. Logos, brand data and photos from Context.dev, copied to R2 (`src/server/lib/images.ts`). Many at once on a short lease. A person adding a company pokes this lane for their organization straight away (`poke.ts`), so the logo appears without waiting for the minute. The company's own favicon (`lib/favicon.ts`: the icons its home page declares, largest declared size first, then `/favicon.ico`, the first that answers as an image) is copied to R2 like any logo, and kept at its source URL if the copy fails. As in the CRM, the poke fetches it at once for a company a person adds or gives a new domain, beside the lane rather than after its brand; and a brand that leaves a company without an icon (no Context.dev key, or no icon in its answer) falls back on it. It is free, and a later brand with an icon replaces it. The `slack-sync` task reads the Slack inventory (`docs/maintainers/slack.md`). Where usage is billed, an organization out of credits has its logos and photos wait, since Context.dev bills them; what costs nothing (`FREE_KINDS`: the Slack read) never waits, and neither do favicons.
- **Research** (everything else but CRM events): one `CrmAgent` session per task, on a lease long enough to finish and report back. A failed task is retried when its lease runs out, up to a limit, then retired.

Each session has a research budget (`runtime/budget.ts`): how many paid lookups it may make before it writes up, priced as the CRM priced them. A lookup (a brand, a person, a page extraction, a search for someone's profiles) costs 2 units, a quick `research_person` question 1 and a deep one 2, and checking an X handle nothing. Units only ration lookups: every call is billed at its real cost whatever it costs in units. Running out ends the session with a write-up, not an error. A session's tokens are capped too, at the CRM's limits, counted as its runtime counted them: the provider's usage, added up across the session's turns (and a research task's attempts) in the session's own storage, and checked before each model call, so the call that crosses a limit finishes. A research session or a chat has the CRM agent's 500,000 input and 50,000 output tokens; past them, `CrmAgent.beforeStep` takes its tools away and tells it to write up what it has, so it ends the same way. The research agent and record chats search the web with OpenRouter's server-side search, as the builder does (Team agents, below), billed in the model call. A company's brief (`research_company`) is one lookup that reads up to eight pages of its site (Context.dev's web extract, `maxPages: 8`, as the CRM asked), and so is the search of an employer's site for a contact's photo. On a first-party deployment, `FIRST_PARTY_SCHEDULED_RESEARCH=off` holds the research lane to work a person asked for (`src/server/lib/deployment-tier.ts`). Research the model can't do waits rather than fails. The gateway's AI proxy has no status route, so the CRM learns whether a model key exists from its answers (`services/AgentAvailabilityService.ts`): a session refused with `ai_provider_not_configured` records the refusal on the organization's workspace row and hands its task back with the attempt uncounted, and the model's next answer clears it. The dispatcher leaves a refused organization's research for ten minutes, then tries again, so a key set later is picked up with nobody doing anything; with no gateway binding at all (local dev without a key) it leases no research. Records, Overview's queue and the Agent tab show such work as "Waiting for setup" and stop polling for it.

A CSV import queues the same work as adding records by hand, paced (`AgentTaskService.recordsImported`): logos at once, below a person's own adds; everything that needs the model at the lowest priority but rechecks, two records a minute after any earlier import's bookings.

Beside the lanes, the cron fills contact fields that went blank from the agent's waiting suggestions (`lib/blankFacts.ts`).

## The enrichment sweep

Ported from the CRM's automatic backfill (`BackfillService`), the sweep (`dispatch/sweep.ts`, `repositories/AgentSweepRepository.ts`) queues work; the lanes do it. Two passes cost nothing, so the sweep does them itself first, as the CRM's backfill did, whatever the organization's credits and with the scheduled research held: the favicon of each company with a domain and no icon (`sweepFavicons`), and a copy in R2 of each logo or icon still at its source URL because its copy failed (`ImageMirrorService`; none at all without picture storage). The CRM's 25 of each a run, five at a time, after the sweep's research is queued and at most 50 companies a tick across organizations (each a handful of fetches); a company's latest attempt is kept as a finished `favicon` or `image-copy` task, so it is tried at most once a day, where the CRM tried the same oldest 25 on every sweep. The CRM's mirror also copied contacts' photos and its users' avatars; here a photo is only ever stored once copied, and members have no avatar to copy. For each organization it queues:

- the workspace's own profile, when it has a website and no profile, and no attempt in a week;
- a brand and a company profile (`PRIORITY.brand`, `PRIORITY.sweep`) for companies with a domain never successfully looked up: still PENDING, or FAILED with no brand attempt in a day;
- a brand for companies with neither logo nor icon and no brand attempt in 30 days (the brand falls back on the favicon);
- a portrait (`PRIORITY.portrait`) for contacts with no photo and somewhere to look (a GitHub profile; with Context.dev, a LinkedIn profile or the employer's website) and no photo search in 30 days;
- `identify` (`PRIORITY.sweep`) for contacts never successfully researched, with no attempt in a day, in whatever room the photos leave of the 500 a run.

At most 500 records of each kind a run, oldest first, archived records never. A brand lookup with no Context.dev key leaves its company PENDING, so the companies and photos that need Context.dev are queued on the first sweep that finds the key on the gateway (`hasContextAccess`), where the CRM queued them when a person saved the key.

The CRM swept when someone signed in, at most every five minutes. Here the gateway signs people in, so the minute cron sweeps each organization at most every five minutes, the 20 that have waited longest each tick (`DISPATCH.enrichment`, `workspace.enrichment_swept_at`). A failed record is retried at most once a day, where the CRM retried it on every sweep: on a five-minute cadence that would research the same failure all day. What the sweep queues is scheduled research: `FIRST_PARTY_SCHEDULED_RESEARCH=off` holds it, and an organization out of credits gets nothing queued.

## Health checks

`src/server/features/health/healthRoutes.ts`, as the CRM's API and agent reported their health:

- `GET /health`, public (declared in `everyapp.config.ts`): one query, `200 {"status":"ok","database":"up"}` or `503 {"status":"error","database":"down"}`, and a warning in the logs when the query takes over 250 ms. It says nothing about any organization.
- `GET /health/dispatch`, for monitoring: the gateway turns away a caller who isn't signed in before the CRM sees the request. An owner or admin calls it with their session, or a personal access token for the CRM that holds `*` (what the gateway's tokens page makes) or, made through the gateway's API, only the `health` scope; anyone else, a deploy key included, gets 403 and no counts. It answers with when each lane of the minute cron last ran and last failed (`dispatcher_lane`, the deployment's, one row per lane, written each tick in `scheduled.ts`), and for the caller's organization only: each lane's backlog, its oldest due item, how much is overdue, and what failed in the last day (tasks retired after their attempts, failed runs). It is `503` when the visible, research or runs lane hasn't run in five minutes, or work has been due for five minutes and not taken. Work held on purpose (out of credits, no model, scheduled research off) is reported as held, not overdue, and a queued run waiting for its agent's run before it isn't overdue either.

## The evidence ledger

What the agent learns about a person is a fact in `contact_fact`, priced by its evidence (`lib/evidence.ts`, `lib/facts.ts`, whose header states the rules). A blank field is filled; a value already there is replaced only by verified evidence; anything weaker becomes a suggestion a person accepts or dismisses on the contact sheet. The agent owns a column only while it still holds the value the agent wrote, so a person's correction is never overwritten. A dismissed value is never offered again.

## Chats

The Agent tab on every record talks to its own `CrmAgent` session over `/agents/crm-agent/<session>`. Session names are minted by the server (`sessionName.ts`) and carry the organization; `agentRoutes.ts` checks every connect and read against the caller's organization and their own conversation, and research sessions are never reachable from a client. Sockets close after 15 minutes and the client reconnects. The open conversation is in the URL (`thread`, as the CRM's record stack kept it), so a reload or a link opens it again.

A conversation is one session, so its tokens are capped across all its turns (The dispatcher, above): the turn that spends them writes up what it has, and a message after that gets "This conversation has hit its token limit. Start a new conversation." (in a builder chat, "This chat has hit its token limit. Start a new chat.") instead of a turn, with no model call. The CRM's runtime paused a spent session on an Approve or Stop prompt that the CRM's chats never showed, so a spent chat stopped mid-turn and later messages got no answer.

The Worker passes the caller's gateway role to the session for the tools only an owner or admin may use (managing custom fields). Two tools pause for approval in a chat (`record_job_change`, `archive_field`): the Agent tab renders the request and answers it with `addToolApprovalResponse`; a pending request survives a reload. `ask_question` is a client tool: the agent asks a person to choose between candidates, and the answer resumes the turn. As in the CRM, a question has a display (confirmation, select or text), options each with an id and a style, and takes typed text only when it allows it (`src/shared/agent-question.ts`); a letter key picks an option. `CrmAgent` checks every answer before Think takes it and refuses an option the question doesn't offer, text it doesn't take, and a second answer (`team-agents/runtime/answers.ts`).

## Team agents

A team describes an agent in a private builder chat ("every Monday, summarize the deals that slipped"), reviews the version the builder saved, deploys it, and it runs by hand, on a schedule or on CRM events, with a ledger of everything it did. Ported from the CRM's `agent_builder` and `agent_runner`; here both are sessions of the same `CrmAgent` runtime with their own instructions and tools, not a second agent framework (`src/server/features/team-agents`, tables in `src/db/team-agent.schema.ts`).

**The builder** is a builder chat: an `agent_conversation` of kind `BUILDER`, talked to over the same socket as a record chat and authorized the same way. Its tools (`runtime/builderTools.ts`) are the research agent's free CRM reads and `list_fields`, `inspect_context` (the CRM event catalog, the Slack inventory, whether captured email and meetings can be granted, the records and integrations tagged in the chat, any draft and the time) and `read_attachment`. A question also gets the research agent's people and company research (`research_person`, `research_company`, the LinkedIn lookups, `find_contact_socials`), paid from the turn's research budget as in a record chat, and the CRM chat's own web tools: `web_fetch` and `web_search`. The CRM's `web_search` was the one its model's provider ran (the AI Gateway's Parallel search); here it is OpenRouter's web search server tool on the same engine, which searches inside the model call, is billed in that call's cost and shows no step of its own. A turn that asks for an agent gets `write_agent_file` and `save_agent_draft` instead, and they close for the rest of the turn once a draft is saved. Asking is the CRM's rule (`src/shared/builder-command.ts`): "/Create agent" (the composer's Create agent switch) or a request in words ("set up an agent that…"), not a question about agents; the composer switches Create agent on as it reads one. Chat's column shows a chat working while its `CrmAgent` says a turn is answering (`isAnswering`, Think's stream state); only a chat whose last turn started in the last 30 minutes without a reply is asked. Clarifying questions are `ask_question`, answered in place of the composer; the builder's tools declare it themselves, so the turn that answers a chat's first message can ask too. A chat started from Chat home or from Slack's New agent is one replay-safe call (`BuilderService.startConversation`): it keeps the first message's files and hands the message to the chat's `CrmAgent`, and leaves nothing behind when either fails; the client picks the chat's id, so a retry finds the chat its first try started. A build has the CRM builder's limits: 12 tool calls and 2 draft saves a turn, and 100,000 input and 10,000 output tokens from the message that asked for it, within the chat's own. Past its tokens a build writes up where it got to, with no more tools, and the chat goes on. The CRM's build was a subagent that never saw the chat; here a build is the chat's turn and re-reads the chat each step, so a build late in a long chat reaches its 100,000 sooner. A Slack channel can be tagged (`slack:channel:<id>`), and `inspect_context` names it. Tagged records and attached files ride on the person's message metadata; the tools re-read every tagged record from the organization and use the CRM's own labels. The model gets them as the CRM's builder sent a submission: `prepareBuilderTurn`'s `messages`, which `CrmAgent.beforeTurn` hands Think, put `Tagged resources: <labels>` before each message's text, with the labels the message was sent with, and add its images and PDFs as file parts: only from the messages Think replays in full (it hides older media from the model), and at most 10 MB a turn, newest first. Attachments are kept in R2 under a prefix the image route never serves, readable only by the chat's owner; the builder reads text files with `read_attachment`.

**Sharing a builder chat** (`src/server/features/sharing`): its owner can let anyone in the workspace with the link read it, as the CRM's Share dialog did. A chat has at most one link, an `agent_conversation_share` row holding only the SHA-256 of the link's 32 random bytes, so the link is shown once, when it is made; replacing it overwrites the hash and revoking it deletes the row, so an old link stops at once. Opening a link finds the row in the opener's own organization (anyone else gets not found) and reads the transcript from the chat's `CrmAgent` on the server: the socket stays the owner's alone, and the page has no composer, ratings, answers or review. The chat's attachments open with the link's token (`?share=` on the attachment route).

**Versions** are immutable. `save_agent_draft` validates the draft (`services/draft.ts`: a selected scope names only tagged records, event triggers need workspace scope, a Slack destination is one the inventory holds, email and calendar need a connected mailbox or calendar in the workspace, every agent has a run summary, a schedule is in the future and recurs from every minute to once a year) and saves a READY version with its triggers (disabled), its exact files and an audit line, in one batch. The chat's first save creates the agent as a DRAFT only its creator sees, and names the chat after it. **Deploying is the approval boundary**: a person (the creator, or an owner or admin) deploys an exact version; it alone becomes DEPLOYED and its triggers alone are enabled. Changing a deployed agent from its page (actions off, a new Slack channel, fewer records, chosen records for a workspace-wide agent with no event trigger, no captured email or meetings, edited instructions or README) makes a new deployed version at once and moves its triggers over. Giving it more (another record, captured email or meetings) or editing its manifest makes a READY version instead, checked as `save_agent_draft` checks a draft, except that the Slack destination the deployed version posts to isn't checked again (a channel renamed since takes its new name), with its own triggers off until a person deploys it (`services/revisionVersions.ts`); a schedule it carries keeps its cadence from the next slot ahead.

**Runs** are `agent_run` rows. A manual run, a due schedule slot (`schedule:<trigger>:<slot>`) and a matched CRM event (`event:<event task>:trigger:<trigger>`) each queue one run keyed by what caused it, so a replayed request, two overlapping crons or an event handled twice make one run. **CRM events can't be lost.** The CRM wrote each one in the transaction of the record write that caused it (`withCrmEvents`); here the write's batch carries it (`queueCrmEvents` in `AgentTaskRepository.ts`), as an `agent-event` task with the CRM's payload: the type, the record, when, and the CRM's data (a contact's `email` included). The CRM's emitters are ported: a company a person adds or one added for an email domain, a contact a person adds or one captured from mail or a meeting, a new deal and a deal's stage change. An event commits exactly when its record does, and a stage move someone else made first takes its events back out in the same batch. `TriggerService.queueEventRuns` leases pending events, queues a run for each live agent listening and closes them: for one organization in a poke right after the write, and for everyone on the minute cron, which catches whatever a poke missed. An event that fails is tried again when its lease runs out, like any task. The minute cron's team-agent lane (`runtime/dispatch.ts`) fails runs that ran past 20 minutes, returns undelivered ones to the queue, queues due schedules and the runs of pending events, and starts queued runs one at a time per agent (a partial unique index allows one RUNNING run per agent) in a `run.<organization>.<run id>` session. A person's Run now pokes the lane for their organization at once. A run that can't run says why instead of waiting: no model on the gateway, Slack not connected, an unreadable manifest.

**The runner** (`runtime/runnerTools.ts`) gets the version's approved instructions as system context and only the tools its manifest grants: `inspect_run`, `query_crm`, `list_deals`, `read_crm_record`, `create_crm_activity` when an activity type is granted, `post_slack_message` when a Slack destination is pinned, `web_search`, `web_fetch` and `finish_run`. The runner's `web_search` (a quick Sonar question from the run's research budget) and `web_fetch` are this port's addition: the CRM's runner had both switched off. `web_fetch` (`runtime/webFetch.ts`, the builder chat's too, where it stands for the CRM's harness tool) is one https request of at most 5 MB, HTML as markdown, and a redirect handed back instead of followed, so `refusedUrl` (`src/server/lib/publicUrl.ts`) checks every URL before it is fetched and refuses IP addresses, localhost and the Every App gateway's own hosts. Every call re-reads the run and its version and enforces the grant itself (records only in scope, only a granted activity type, Slack only to the pinned destination, captured mail and meetings only when granted), whatever the model asked.

**Captured email and meetings** are two grants a version can carry, the CRM's `google:gmail` and `google:calendar` integrations (here `capture:email` and `capture:calendar`, in `CAPTURE_GRANTS`, `src/shared/team-agents.ts`). Capture is per member but filed on shared records, so a grant is to the organization's captured threads and meetings on the records the version may see, Gmail and Outlook alike: the runner never touches a mailbox or a token. The builder offers them (tag Email or Calendar in the composer; `inspect_context` reports `availableConnections.email` and `.calendar`) only once some member has connected a mailbox or a calendar, and `save_agent_draft` refuses them before that; the access list and the review say so in plain words. `read_crm_record` reads a record's history through the research agent's history reads with the version's sources: an ungranted source is never queried, its lists come back empty, its counts null and a `withheld` line says why. Whatever capture excludes stays excluded: suppressed people and domains are never filed on records, and a member's "Delete synced data" removes the rows the reads would find. Changing a deployed agent from its page takes a grant away at once; adding one makes a version that waits for review.

**The action ledger** (`agent_action`): every side effect is a row before it happens, keyed by the run and the model's tool call id, with a hash of the request. A replayed call finds a succeeded action and returns it; the same call id with other input is refused; a claim is a conditional update with a lease, re-checked just before a Slack message leaves. When a run ends, any declared action that never succeeded fails it, unless the run rightly reported that nothing was needed (only schedule and event runs may).

**Stopping a run is a row, not a signal.** Cancelling settles the run to CANCELLED with a conditional write; its winner cancels the outstanding actions and writes the terminal event and the audit line. Every runner tool refuses a run that is not RUNNING, so a stop that never reaches the session still means nothing more is written; the poke to the session only stops it spending. What it already did stays done. Who may stop it: whoever started it, the agent's creator, an owner or admin.

**Spending.** Runs are model calls the gateway's keys pay for. Each run has the CRM runner's 500,000 input and 40,000 output tokens, counted as a chat's are; past them its next model call fails, so the run fails as the CRM's did (TURN_FAILED, "The session reached its configured input token limit."). The CRM set no step limit, so a run's 100 steps are only a safety bound that its input tokens reach first. A step writes at most 8,000 output tokens, as other background work does, and a run's research budget is two quick web questions. As in the CRM, an agent runs one run at a time, a run is stopped after 20 minutes, and a schedule may recur as often as every minute, with no daily cap on runs. Where usage is billed, credits bound the rest (`billing.md`): a schedule's or an event's run is skipped and audited while the workspace is out of credits. On a first-party deployment, `FIRST_PARTY_SCHEDULED_RESEARCH=off` holds scheduled runs with the scheduled research, and closes CRM events without runs: one switch for the deployment's unattended spending. Runs a person starts always run.

The CRM had no webhook triggers or per-action approval to port: `WEBHOOK` was a trigger type with nothing to receive it, and nothing ever set a run `WAITING_FOR_APPROVAL`. Runs are unattended; the deployed permissions are the boundary.

## Changing it

- A new tool family is a `ToolGroup` in `tools/registry.ts`; tools run as the session's organization, with their output capped and failures handed back to the model.
- Prompts are in `prompt/`, and the agent's longer guidance in `skills/*.md`.
- Tests stub every vendor call; nothing in the suite spends money.

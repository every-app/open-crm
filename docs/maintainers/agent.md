# The research agent

The CRM keeps its records up to date with a research agent ported from the CRM's agent (which ran on Vercel). Here it is a [Think](https://developers.cloudflare.com/agents/) agent in a Durable Object (`CrmAgent`, `src/server/features/agent/CrmAgent.ts`), driven by a queue in the database and the Worker's minute cron. Every model and Context.dev call goes through the Every App gateway, named for the organization it is for (`docs/maintainers/every-app.md`).

**The model** is GPT-6 Luna through OpenRouter, set up as OpenSEO runs Luna (`src/server/lib/openrouter.ts`), with MiniMax M3 where OpenAI is blocked, and nobody picks it in the app; a self-hosted copy sets `OPENROUTER_MODEL` to use another. As OpenSEO splits it, a person's chat turn (a record chat or Chat) reasons at `max` with 16,000 output tokens a step, and background work (research sessions, team agent runs, compaction summaries) at `low` (`runtime/model.ts`, `runtime/turn.ts`). A run records the model it ran on.

## The queue

`agent_task` says what the work is: a kind (`src/shared/agent-tasks.ts`), a subject (a company, contact, deal or the workspace), a reason, a priority and when it is due. A partial unique index allows one open task per organization, kind and subject, so queueing the same work twice is a no-op (`AgentTaskRepository.insertIfAbsent`). Anything that recurs ("check again in 30 days") is a task's `due_at`, never a timer.

Work is queued by the features that cause it, through `AgentTaskService`: a new company or contact, a changed workspace website, a new or backfilled custom field the agent fills, a person asking for a recheck.

## The dispatcher

The minute cron (`src/server/cron.ts` → `scheduled.ts`) closes stale tasks, then drains two lanes across every organization (`dispatch.ts`, numbers in `dispatch/config.ts`):

- **Visible** (`brand`, `portrait`): no model. Logos, brand data and photos from Context.dev, copied to R2 (`src/server/lib/images.ts`). Many at once on a short lease. A person adding a company pokes this lane for their organization straight away (`poke.ts`), so the logo appears without waiting for the minute.
- **Research** (everything else): one `CrmAgent` session per task, on a lease long enough to finish and report back. A failed task is retried when its lease runs out, up to a limit, then retired.

Each session has a research budget (`runtime/budget.ts`): every billable lookup costs 2 units, and running out ends the session with a write-up, not an error. On a first-party deployment, `FIRST_PARTY_SCHEDULED_RESEARCH=off` holds the research lane to work a person asked for (`src/server/lib/deployment-tier.ts`). Research the model can't do waits rather than fails. The gateway's AI proxy has no status route, so the CRM learns whether a model key exists from its answers (`services/AgentAvailabilityService.ts`): a session refused with `ai_provider_not_configured` records the refusal on the organization's workspace row and hands its task back with the attempt uncounted, and the model's next answer clears it. The dispatcher leaves a refused organization's research for ten minutes, then tries again, so a key set later is picked up with nobody doing anything; with no gateway binding at all (local dev without a key) it leases no research. Records, Overview's queue and the Agent tab show such work as "Waiting for setup" and stop polling for it.

A CSV import queues the same work as adding records by hand, paced (`AgentTaskService.recordsImported`): logos at once, below a person's own adds; everything that needs the model at the lowest priority but rechecks, two records a minute after any earlier import's bookings.

Beside the lanes, the cron fills contact fields that went blank from the agent's waiting suggestions (`lib/blankFacts.ts`).

## The evidence ledger

What the agent learns about a person is a fact in `contact_fact`, priced by its evidence (`lib/evidence.ts`, `lib/facts.ts`, whose header states the rules). A blank field is filled; a value already there is replaced only by verified evidence; anything weaker becomes a suggestion a person accepts or dismisses on the contact sheet. The agent owns a column only while it still holds the value the agent wrote, so a person's correction is never overwritten. A dismissed value is never offered again.

## Chats

The Agent tab on every record talks to its own `CrmAgent` session over `/agents/crm-agent/<session>`. Session names are minted by the server (`sessionName.ts`) and carry the organization; `agentRoutes.ts` checks every connect and read against the caller's organization and their own conversation, and research sessions are never reachable from a client. Sockets close after 15 minutes and the client reconnects.

The Worker passes the caller's gateway role to the session for the tools only an owner or admin may use (managing custom fields). Two tools pause for approval in a chat (`record_job_change`, `archive_field`): the Agent tab renders the request and answers it with `addToolApprovalResponse`; a pending request survives a reload. `ask_question` is a client tool: the agent asks a person to choose between candidates, and the answer resumes the turn.

## Team agents

A team describes an agent in a private builder chat ("every Monday, summarize the deals that slipped"), reviews the version the builder saved, deploys it, and it runs by hand, on a schedule or on CRM events, with a ledger of everything it did. Ported from the CRM's `agent_builder` and `agent_runner`; here both are sessions of the same `CrmAgent` runtime with their own instructions and tools, not a second agent framework (`src/server/features/team-agents`, tables in `src/db/team-agent.schema.ts`).

**The builder** is a builder chat: an `agent_conversation` of kind `BUILDER`, talked to over the same socket as a record chat and authorized the same way. Its tools (`runtime/builderTools.ts`) are the research agent's free CRM reads and `list_fields`, `inspect_context` (the CRM event catalog, the Slack inventory, whether captured email and meetings can be granted, the records and integrations tagged in the chat, any draft, the time and the limits) and `read_attachment`. A question also gets the research agent's people and company research (`research_person`, `research_company`, the LinkedIn lookups, `find_contact_socials`), paid from the turn's research budget as in a record chat. A turn that asks for an agent gets `write_agent_file` and `save_agent_draft` instead, and they close for the rest of the turn once a draft is saved. Asking is the CRM's rule (`src/shared/builder-command.ts`): "/Create agent" (the composer's Create agent switch) or a request in words ("set up an agent that…"), not a question about agents; the composer switches Create agent on as it reads one. Chat's column shows a chat working while its `CrmAgent` says a turn is answering (`isAnswering`, Think's stream state); only a chat whose last turn started in the last 30 minutes without a reply is asked. Clarifying questions are the chat client's `ask_question`, answered in place of the composer. Tagged records and attached files ride on the person's message metadata; the server re-reads every tagged record from the organization and uses the CRM's own labels. Attachments are kept in R2 under a prefix the image route never serves, readable only by the chat's owner; the builder reads text files with `read_attachment` and is told the name and type of anything else.

**Versions** are immutable. `save_agent_draft` validates the draft (`services/draft.ts`: a selected scope names only tagged records, event triggers need workspace scope, a Slack destination is one the inventory holds, email and calendar need a connected mailbox or calendar in the workspace, every agent has a run summary, a schedule is in the future and repeats no more often than every 30 minutes) and saves a READY version with its triggers (disabled), its exact files and an audit line, in one batch. The chat's first save creates the agent as a DRAFT only its creator sees. **Deploying is the approval boundary**: a person (the creator, or an owner or admin) deploys an exact version; it alone becomes DEPLOYED and its triggers alone are enabled. Changing a deployed agent from its page (actions off, a new Slack channel, fewer records, no captured email or meetings, edited instructions or README) makes a new deployed version at once and moves its triggers over. Giving it more (another record, captured email or meetings) or editing its manifest makes a READY version instead, checked as `save_agent_draft` checks a draft, with its own triggers off until a person deploys it (`services/revisionVersions.ts`); a schedule it carries keeps its cadence from the next slot ahead.

**Runs** are `agent_run` rows. A manual run, a due schedule slot (`schedule:<trigger>:<slot>`) and a matched CRM event (`event:<event>:trigger:<trigger>`) each queue one run keyed by what caused it, so a replayed request, two overlapping crons or an event delivered twice make one run. CRM events are emitted where the records' services hand work to the queue (`AgentTaskService.crmEvent`, from company, contact and deal creation and deal stage changes); an organization with no live agent listening for the event writes nothing. The minute cron's team-agent lane (`runtime/dispatch.ts`) fails runs that ran past 20 minutes, returns undelivered ones to the queue, queues due schedules, and starts queued runs one at a time per agent (a partial unique index allows one RUNNING run per agent) in a `run.<organization>.<run id>` session. A person's Run now pokes the lane for their organization at once. A run that can't run says why instead of waiting: no model on the gateway, Slack not connected, an unreadable manifest.

**The runner** (`runtime/runnerTools.ts`) gets the version's approved instructions as system context and only the tools its manifest grants: `inspect_run`, `query_crm`, `list_deals`, `read_crm_record`, `create_crm_activity` when an activity type is granted, `post_slack_message` when a Slack destination is pinned, `web_search`, `web_fetch` and `finish_run`. Every call re-reads the run and its version and enforces the grant itself (records only in scope, only a granted activity type, Slack only to the pinned destination, captured mail and meetings only when granted), whatever the model asked.

**Captured email and meetings** are two grants a version can carry, the CRM's `google:gmail` and `google:calendar` integrations (here `capture:email` and `capture:calendar`, in `CAPTURE_GRANTS`, `src/shared/team-agents.ts`). Capture is per member but filed on shared records, so a grant is to the organization's captured threads and meetings on the records the version may see, Gmail and Outlook alike: the runner never touches a mailbox or a token. The builder offers them (tag Email or Calendar in the composer; `inspect_context` reports `availableConnections.email` and `.calendar`) only once some member has connected a mailbox or a calendar, and `save_agent_draft` refuses them before that; the access list and the review say so in plain words. `read_crm_record` reads a record's history through the research agent's history reads with the version's sources: an ungranted source is never queried, its lists come back empty, its counts null and a `withheld` line says why. Whatever capture excludes stays excluded: suppressed people and domains are never filed on records, and a member's "Delete synced data" removes the rows the reads would find. Changing a deployed agent from its page takes a grant away at once; adding one makes a version that waits for review.

**The action ledger** (`agent_action`): every side effect is a row before it happens, keyed by the run and the model's tool call id, with a hash of the request. A replayed call finds a succeeded action and returns it; the same call id with other input is refused; a claim is a conditional update with a lease, re-checked just before a Slack message leaves. When a run ends, any declared action that never succeeded fails it, unless the run rightly reported that nothing was needed (only schedule and event runs may).

**Stopping a run is a row, not a signal.** Cancelling settles the run to CANCELLED with a conditional write; its winner cancels the outstanding actions and writes the terminal event and the audit line. Every runner tool refuses a run that is not RUNNING, so a stop that never reaches the session still means nothing more is written; the poke to the session only stops it spending. What it already did stays done. Who may stop it: whoever started it, the agent's creator, an owner or admin.

**Spending.** Runs are model calls the gateway's keys pay for. Each run has 16 steps, 4,000 output tokens a step, a research budget of two web searches, and stops where it is past 300,000 input tokens; an agent starts at most 50 runs in any 24 hours (a schedule or event run over the cap is skipped and audited), and a schedule repeats at most every 30 minutes. On a first-party deployment, `FIRST_PARTY_SCHEDULED_RESEARCH=off` holds scheduled and event runs with the scheduled research: one switch for the deployment's unattended spending. Runs a person starts always run.

Not ported: builder-chat sharing by link (builder chats are private drafts; the agent's page is what the team sees), webhook triggers, per-action approval in a run (runs are unattended; the deployed permissions are the boundary), and the builder seeing images or PDFs.

## Changing it

- A new tool family is a `ToolGroup` in `tools/registry.ts`; tools run as the session's organization, with their output capped and failures handed back to the model.
- Prompts are in `prompt/`, and the agent's longer guidance in `skills/*.md`.
- Tests stub every vendor call; nothing in the suite spends money.
